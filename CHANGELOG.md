## [0.3.1] - 2026-10-15

Commit [`61bd5cd`](https://github.com/jameshuntt/waker_protocol/commit/61bd5cdb15187681a581f455c2aa621ceb5de460), tag `v0.3.1`, published by the CI `publish` job ([run](https://github.com/jameshuntt/waker_protocol/actions/runs/38699175518)). `cargo package` at this commit gives sha256 `dbb2875b…`, the same checksum crates.io has for 0.3.1.

These are fixes from a review of 0.3.0. No public signature changed. "Before" below means the 0.3.0 code ([`1ca72a5`](https://github.com/jameshuntt/waker_protocol/commit/1ca72a5803549914aa822c42cbb91705e267875f)) with the 0.3.1 tests dropped in; "after" means `61bd5cd`. ### Fixed

**A refused or failed message no longer destroys its task.** In 0.3.0, `poll_one` took the task out of its row and then returned `Err` early when a message was written for another task type, or when a message's `deliver` fn returned `Err`. The task was dropped right there, with no checkpoint. Its row stayed `Resident::Empty` and `Runnable` for good: `poll_one` skips an `Empty` row, while Wake and Deliver keep pushing onto it, so every later wake and message piled up on a task that was never polled again. Now only that message is dropped. The task stays live, its other messages are delivered, and it is polled as usual.
- Was: [`poll_one` takes the task out of its row](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L657-L663), then [returns early on a type mismatch or a failed `dispatch`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L669-L680). [Wake and Deliver](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L399-L414) keep queueing onto the dead row.
- Now ([`61bd5cd`](https://github.com/jameshuntt/waker_protocol/commit/61bd5cdb15187681a581f455c2aa621ceb5de460)): [`poll_one` notes each delivery error and keeps going](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/src/scheduler.rs#L661-L689), and [`deliver`](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/src/scheduler.rs#L691-L705) drops one envelope and leaves the task alone.

**A round finishes before it reports an error.** In 0.3.0, `run_once` and `pump` stopped at the first `Err`. [`poll_ready`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L491-L508) collected finished tasks in `to_remove` and removed them only after the loop, so an error later in the round skipped the removal. Those tasks stayed as dead `Completed` rows, and their checkpoints stayed in the store even with `retain_on_completion` off. Nothing removed them later, because [a `Completed` row with nothing queued is never runnable](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L105-L109). Now every error is collected in [`Errors`](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/src/scheduler.rs#L135-L154) and returned once the round is done, joined with `"; "`. [`poll_ready`](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/src/scheduler.rs#L601-L609) removes a task at the point it finishes, and a task that cannot be restored stays dormant while the round goes on.
- Proof: [`an_error_never_skips_removing_tasks_that_finished_earlier_in_the_round`](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/tests/scheduler.rs#L609-L628). Before, it panics with `the finished task is removed in the same round`. After, it passes. Fix in [`61bd5cd`](https://github.com/jameshuntt/waker_protocol/commit/61bd5cdb15187681a581f455c2aa621ceb5de460).

**A failed checkpoint save keeps the task.** In 0.3.0 every checkpoint path took the task out of its row, called `checkpoint()`, then `self.store.save(id, payload)?`. If the store failed (disk full, network down), the `?` dropped the task: no saved bytes, no live copy, and a row left `Resident::Empty`. That held for [a Checkpoint or Capitulate message and Shutdown](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L562-L573), [a strategy plan](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L690-L697), [`TaskPoll::Checkpoint`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L767-L771) and [`TaskPoll::Capitulate` with a stub](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L801-L806). Now all of them go through one function, [`checkpoint_live`](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/src/scheduler.rs#L749-L783), which frees the task only after `save` returns `Ok`. On `Err` the task goes back in its row, live and as it was, and the error is returned.

**Shutdown returns its errors, then stops.** Two problems in 0.3.0. First, the Shutdown arm did [`let _ = self.force_checkpoint(..)`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L429-L435). With a failing store every live task was freed with nothing saved, and `pump` still [returned `Ok(false)`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L381), a clean stop. Second, it did not stop. [`pump`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L367-L382) checked `shutdown` only on entry and then still ran `drain_inbox` and `poll_ready`, and [`run_once`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L360-L365) never checked it. A task with a message queued before Shutdown, or a wake sent after it, was restored from its shutdown checkpoint and polled again, so the checkpoint anything would hand off from was already stale. Now the Shutdown arm [notes every failed save](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/src/scheduler.rs#L542-L547), and a task whose save failed stays live in its row. Once Shutdown is handled, [`round` and `drain_inbox`](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/src/scheduler.rs#L496-L512) restore and poll nothing: messages sent after it stay in the channel, and messages and wakes queued before it stay in the task's row. To retry after a failed save, set `shutdown` back to `false` and send Shutdown again.

**The capitulation strategy sees the work that is waiting.** In 0.3.0, `poll_one` [delivered the mailbox and the pending wakes](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L669-L687) and only then [built the `TaskSnapshot`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L690-L693), so `mailbox_len` and `pending_wakes` were always 0. The default idle rule [checks that both are 0](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/capitulate.rs#L102-L113) to spare a task with work waiting, so that check never did anything. And `last_polled_at` is [set only when the task is actually polled](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L729-L733). So once a task at Standard or below, with a footprint of at least `min_footprint_bytes`, sat idle past `idle_before_checkpoint`, every wake restored it, the strategy checkpointed it again as `Idle`, and its `poll` never ran again. Now [the snapshot is taken first](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/src/scheduler.rs#L665-L667), before anything is delivered, and `footprint_bytes` is read then too. A restore pushes `Resume`, so a woken task counts as having work and gets polled. If the strategy does return a plan, the messages and wakes are [still delivered before the checkpoint](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/src/scheduler.rs#L669-L679), so the checkpoint holds them.

[`the_idle_rule_checkpoints_a_task_with_no_waiting_work_and_a_wake_brings_it_back`](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/tests/scheduler.rs#L865-L881): before, `woken, restored and polled`, `left: 1, right: 2`; after, it passes. Fix in [`61bd5cd`](https://github.com/jameshuntt/waker_protocol/commit/61bd5cdb15187681a581f455c2aa621ceb5de460).

**`retain_stub: false` ends the task, wherever the plan comes from.** [`CapitulatePlan::retain_stub`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/capitulate.rs#L9-L10) says false means finish and be removed. `TaskPoll::Capitulate` did that, but [the strategy branch of `poll_one`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L693-L725) never read `retain_stub`: it always checkpointed and went dormant. So a custom `CapitulateStrategy` could not evict a task, and the next wake brought it back. A Capitulate message without a stub went to [`finalize_removal` with whatever state the task had](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L612-L618), and [`finalize_removal`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L869-L875) kept a dormant task's latest checkpoint and deleted a waiting task's, whatever the retention policy said. Now all three go through [`Settle::capitulate`](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/src/scheduler.rs#L169-L177) ([poll](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/src/scheduler.rs#L187), [strategy](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/src/scheduler.rs#L678-L679), [message](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/src/scheduler.rs#L536-L537)): no stub means the task ends as `Completed`, and `retain_on_completion` decides its checkpoints.

**A wake that comes before a Checkpoint message is kept.** In 0.3.0, [`force_checkpoint` cleared `pending_wakes`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L575-L580). If a wake (from a `scheduler_waker` on another thread, say) and a Checkpoint message landed in the same drain in that order, the wake was thrown away without `on_wake`, and the task stayed dormant until some other wake came. A waker that fires once left it hung for good. A queued message did not have this problem, because the mailbox was not cleared. Now [`checkpoint_live`](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/src/scheduler.rs#L766-L771) leaves `pending_wakes` alone, so the next round restores the task and polls it for the wake.

**Task ids never come back.** [`TaskSlab::remove`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/slab.rs#L61-L71) did `slot.generation.wrapping_add(1)` and pushed the slot back on a [last-in, first-out free list](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/slab.rs#L26), so a scheduler running one short task at a time reuses slot 0 every time. After 2^32 reuses the generation wrapped around to an old value and an old `TaskId` matched the new task, so a stale handle's wake, checkpoint or cancel reached a task it never belonged to. The docs said that could not happen ([slab.rs](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/slab.rs#L8), [types.rs](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/types.rs#L6)). Now a slot whose generation reaches `u32::MAX` is [retired instead of wrapping](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/src/slab.rs#L69-L75). The cost is one empty slot per 2^32 reuses of a slot, and the [docs say so](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/src/slab.rs#L8-L10).

### Changed

**`Yield` docs say what the code does.** Behavior unchanged. [`eager_repoll_after_yield`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/policy.rs#L73-L74) said "Poll again in the same round", and [`TaskPoll::Yield`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/types.rs#L72-L73) said "at once if the policy says eager repoll". A task is polled at most once per round. With the flag on, it is polled again on the next `run_once` or `pump`; with it off, it waits for a wake like `Pending`. New docs: [policy.rs](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/src/policy.rs#L73-L76), [types.rs](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/src/types.rs#L73-L75). **`pump` docs say what stops it.** [The 0.3.0 doc](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L367) said `pump` returns false "once shut down or every handle is gone". The doc was written in 0.3.0; the held sender is from 0.2.0.

**`run_once` and `pump` return every error of the round.** The `Err` is all of them, [joined with `"; "`](https://github.com/jameshuntt/waker_protocol/blob/61bd5cdb15187681a581f455c2aa621ceb5de460/src/scheduler.rs#L147-L153), after the round is done (see Fixed). **`Resident::Empty`** meant ["Gone, or out for a poll"](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L49-L50). ## [0.3.0] - 2026-10-15

Commit [`1ca72a5`](https://github.com/jameshuntt/waker_protocol/commit/1ca72a5803549914aa822c42cbb91705e267875f), tag `v0.3.0`, published by the CI `publish` job ([run](https://github.com/jameshuntt/waker_protocol/actions/runs/38664880979)). The published crate's `.cargo_vcs_info.json` names `1ca72a5`, and its files match that commit except `Cargo.lock`, which cargo writes at publish time.

Moved to waker_tables 0.3, and closed every way we found for safe code to run a task as the wrong type. "Safe code" here means no `unsafe` block at all: the only `unsafe` in the probes below is the `unsafe impl ProtocolTask` the trait requires, with bodies that only touch `self`. `Small` is an 8-byte task and `Big` a 64-byte one, both declared with `derive_protocol_task_vtable!`. Each probe was run against 0.2.1 and 0.3.0 with `MIRIFLAGS=-Zmiri-strict-provenance cargo +nightly miri run`.

### Security

**A task could be run, or freed, through another type's vtable.** In 0.2.x nothing checked the task pointer against the vtable:
- [`spawn_box`](https://github.com/jameshuntt/waker_protocol/blob/85969ac8e14418b382217102d8602dd3f868e60a/src/scheduler.rs#L272-L298) took whatever vtable was registered under the key and paired it with the `Box<T>` it was given.
- [`ProtocolTaskPtr::from_box`](https://github.com/jameshuntt/waker_protocol/blob/85969ac8e14418b382217102d8602dd3f868e60a/src/task.rs#L40-L51) took any `&'static ProtocolVTable`, and both fields of `ProtocolTaskPtr` were `pub`, so a pointer could be built by hand from anything.
- [`ProtocolVTable`'s fields](https://github.com/jameshuntt/waker_protocol/blob/85969ac8e14418b382217102d8602dd3f868e60a/src/task.rs#L22-L30) were `pub`, so a vtable could mix two types' functions.
- [`Drop`](https://github.com/jameshuntt/waker_protocol/blob/85969ac8e14418b382217102d8602dd3f868e60a/src/task.rs#L81-L88) then calls `destroy_fn` on `data`, from safe code.

```rust
sched.register_vtable(key, &BIG_VTABLE);
sched.spawn_box(key, Box::new(Small(1)), TaskPolicy::default()); // Ok(TaskId { slot: 0, generation: 0 })
sched.run_once(); // UB: constructing invalid value of type &mut Big: dangling reference

drop(ProtocolTaskPtr::from_box(Box::new(Small(1)), &BIG_VTABLE)); // UB: dangling box
drop(ProtocolTaskPtr { data: Box::into_raw(Box::new(0u8)).cast(), vtable: &BIG_VTABLE }); // UB: dangling box
```

Miri stops the first one in [the vtable's `wake_fn`](https://github.com/jameshuntt/waker_protocol/blob/85969ac8e14418b382217102d8602dd3f868e60a/src/task.rs#L96-L98) and the other two in [`destroy_fn`](https://github.com/jameshuntt/waker_protocol/blob/85969ac8e14418b382217102d8602dd3f868e60a/src/task.rs#L109-L112). Now ([`1ca72a5`](https://github.com/jameshuntt/waker_protocol/commit/1ca72a5803549914aa822c42cbb91705e267875f)) a `ProtocolVTable` [records the type it was built for, and its fields are private](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/task.rs#L52-L78). It is built only by [`ProtocolVTable::of::<T>()`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/task.rs#L115-L143), which `derive_protocol_task_vtable!` [now calls](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/task.rs#L249-L255). [`ProtocolTaskPtr`'s fields are private, and `from_box` asserts the vtable is for `T`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/task.rs#L155-L177). [`spawn_box` refuses a key whose vtable runs another type](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L321-L341). The same three on 0.3.0: `spawn_box -> Err("protocol vtable for VTableKey { .. } is for ub::Big, not ub::Small")`, a panic `protocol vtable is for ub::Big, not ub::Small`, and `error[E0451]: fields data and vtable of struct ProtocolTaskPtr are private`.
- Tests: [`spawn_refuses_a_key_for_another_type`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/tests/scheduler.rs#L141-L149), [`ptr_from_box_refuses_another_types_vtable`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/tests/scheduler.rs#L350-L360), and [a `compile_fail` doctest](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/task.rs#L58-L68) showing a vtable that lies about its type does not compile.
- Introduced: 0.2.0, [`task.rs`](https://github.com/jameshuntt/waker_protocol/blob/23872ee6f934867c5bc0f79357128dad77531d94/src/task.rs#L22-L51) and [`spawn_box`](https://github.com/jameshuntt/waker_protocol/blob/23872ee6f934867c5bc0f79357128dad77531d94/src/scheduler.rs#L272-L298). 0.2.1 changed no code.

**A message could reach a task of another type, and `dispatch` could be called on any pointer.** In 0.2.x [`Envelope::dispatch`](https://github.com/jameshuntt/waker_protocol/blob/85969ac8e14418b382217102d8602dd3f868e60a/src/envelope.rs#L1-L4) was a safe method that took a `*mut ()`, and [`TypedEnvelope` cast it to `&mut T`](https://github.com/jameshuntt/waker_protocol/blob/85969ac8e14418b382217102d8602dd3f868e60a/src/envelope.rs#L29-L33) without knowing what it pointed at. The scheduler [called it on whatever task the message was queued for](https://github.com/jameshuntt/waker_protocol/blob/85969ac8e14418b382217102d8602dd3f868e60a/src/scheduler.rs#L604-L606), and [`TaskEntry::mailbox` is `pub`](https://github.com/jameshuntt/waker_protocol/blob/85969ac8e14418b382217102d8602dd3f868e60a/src/scheduler.rs#L55), so any `EnvelopePacket` could be queued for any task.

```rust
typed_envelope::<Small, u64>("poke", 7, |t, n| { t.0 = n; Ok(()) })
    .dispatch(std::ptr::null_mut()); // UB: constructing invalid value of type &mut Small: null reference

// `id` is a Small task.
sched.tasks.get_mut(id).unwrap().mailbox.push_back(typed_envelope::<Big, u64>("poke", 7, |t, n| { t.0[7] = n; Ok(()) }));
sched.run_once(); // UB: constructing invalid value of type &mut Big: dangling reference
```

Miri stops both at [the cast in `TypedEnvelope::dispatch`](https://github.com/jameshuntt/waker_protocol/blob/85969ac8e14418b382217102d8602dd3f868e60a/src/envelope.rs#L31). Now [`Envelope` is an `unsafe trait` with `target_type()`, and `dispatch` is an `unsafe fn`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/envelope.rs#L3-L20); [`TypedEnvelope` reports `T`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/envelope.rs#L43-L59), and [the scheduler checks `target_type()` against the task's type before every `dispatch`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L669-L680). On 0.3.0 the first probe does not compile (`error[E0133]: call to unsafe function ... requires unsafe block`), and the second gets `run_once -> Err("envelope \"poke\" for task TaskId { slot: 0, generation: 0 } targets another task type than ub::Small")`.
- Test: [`a_message_for_another_type_is_refused_not_delivered`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/tests/scheduler.rs#L174-L188).
- This fix had a hole. The refusal returned while the task was out of its row, so the task was freed along with the message, and the test only checked that the row was there. Fixed in 0.3.1 (first entry under Fixed).
- Introduced: 0.2.0, [`envelope.rs`](https://github.com/jameshuntt/waker_protocol/blob/23872ee6f934867c5bc0f79357128dad77531d94/src/envelope.rs#L1-L34).

### Fixed

**Cancel frees the task.** In 0.2.x the [Cancel arm](https://github.com/jameshuntt/waker_protocol/blob/85969ac8e14418b382217102d8602dd3f868e60a/src/scheduler.rs#L360-L364) only set `state = Cancelled`. A cancelled task with nothing queued is not runnable, so nothing removed it: its row and its memory stayed until the scheduler was dropped. Now Cancel [calls `finalize_removal`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/src/scheduler.rs#L422-L428) ([`1ca72a5`](https://github.com/jameshuntt/waker_protocol/commit/1ca72a5803549914aa822c42cbb91705e267875f)): the row goes, the task's `cleanup` runs and it is freed, and its checkpoints follow `retain_on_cancel`.
- Proof: spawn a task that counts its drops, cancel it, run 3 rounds. 0.2.1: `row present = true, state = Some(Cancelled), Job drops = 0`, and the drop only came when the scheduler itself was dropped. 0.3.0: `row present = false, Job drops = 1`. Test: [`cancel_removes_and_frees_the_task`](https://github.com/jameshuntt/waker_protocol/blob/1ca72a5803549914aa822c42cbb91705e267875f/tests/scheduler.rs#L249-L259).
- Introduced: 0.2.0, the [same arm](https://github.com/jameshuntt/waker_protocol/blob/23872ee6f934867c5bc0f79357128dad77531d94/src/scheduler.rs#L360-L364).

## [0.2.0] - 2026-10-13

Commit [`23872ee`](https://github.com/jameshuntt/waker_protocol/commit/23872ee6f934867c5bc0f79357128dad77531d94). A rewrite of the 0.1.0 sketch; the old `apoptosis` naming is now `capitulate`.

Published from a copy outside git, so the crate has no `.cargo_vcs_info.json`. `cargo package` on this commit's files outside git gives sha256 `ca7bf079…`, the crates.io checksum for 0.2.0, so the published code is exactly this commit.

### Added

- The `WakerProtocol` scheduler: tasks in a generation-checked slab, run through per-type vtables, with QoS ordering, checkpoints, typed messages, and capitulation, where a task surrenders with a stated reason after a checkpoint so the work can go somewhere else. Every reclaim goes in the reclaim log. Modules: [scheduler, policy, capitulate, checkpoint, envelope, types, slab, task, wake_ref](https://github.com/jameshuntt/waker_protocol/blob/23872ee6f934867c5bc0f79357128dad77531d94/readme.md#L11-L21).
- [Nine examples](https://github.com/jameshuntt/waker_protocol/blob/23872ee6f934867c5bc0f79357128dad77531d94/readme.md#L23-L37), each a full scheduler run that prints its reclaim log. `heav_task` is commented out and runs nothing.

### Changed

- Depends on waker_tables 0.1.4 and crossbeam-channel 0.5.15; tokio is commented out ([Cargo.toml](https://github.com/jameshuntt/waker_protocol/blob/23872ee6f934867c5bc0f79357128dad77531d94/Cargo.toml#L14-L17)).

The soundness holes closed in 0.3.0 and most of the scheduler bugs fixed in 0.3.1 were already in this version; those entries link the 0.2.0 lines.
